- 2026-08-26 — Shell: Tauri 2 (MIT/Apache). Real installer, icon, owns the model server's lifecycle, cross-platform by design.
- 2026-08-26 — Targets: Windows and Linux. macOS dropped (notarization requires a paid Apple account). Mac users may build from source.
- 2026-08-26 — Signing: ship unsigned first (SignPath requires an existing release). Apply to SignPath Foundation after the first public release. README states up front that Windows will show a SmartScreen warning and shows exactly how to proceed.
- 2026-08-26 — Upgrades are manual re-downloads, and the installer upgrades in place: it detects any previous version and replaces it. Never two versions on one machine. User data (history, settings, downloaded models) lives outside the install directory and survives every upgrade; only program and index are replaced.
- 2026-08-26 — Model size: default = one size up from the smallest model that passes evaluation. Installer auto-selects the smaller passing model on machines below the RAM threshold.
- 2026-08-26 — Zero fabricated references, enforced mechanically (5.6), not by prompt alone.
- 2026-08-26 — Question history stored locally; searchable, deletable, exportable. Never leaves the machine.
- 2026-08-26 — Prebuilt index ships inside the installer. The user's machine never parses sources or builds embeddings.
- 2026-08-26 — README opens with a study/educational disclaimer and a crisis note covering harm to self or others. The crisis note also appears in-app above (never instead of) an answer when crisis language is detected.

## P2-prep session, 2026-08-26

- 2026-08-26 — Footnotes and cross-references are omitted from verse text, permanently for v1. Reason: eBible.org permits extracts, listing "quote" among the permitted uses; the WEB trademark condition applies "if you CHANGE the actual text of the World English Bible in any way", and we never change the text, only omit the apparatus around it.
- 2026-08-26 — NOTICE.md WEB entry states plainly that verse text is reproduced unmodified and that translator footnotes and cross-references are omitted. Reason: the one legal obligation on our main source deserves an explicit, checkable statement rather than an inference.
- 2026-08-26 — Eval set is 20 graded questions with MUST and SHOULD gold lists, plus 20 ungraded smoke questions with no gold lists, run in P3 for Jared's eyeball review only. Reason: keeps Jared's approval burden proportionate; the smoke set preserves topic coverage.
- 2026-08-26 — Gold list structure: MUST = 5-8 passages a pastor would say the answer cannot omit, and recall@25 in P2 is measured against MUST only; Jared approves every MUST list. SHOULD = further relevant passages, Claude's draft, non-gating, labeled unreviewed. Reason: only the gating part needs approval.
- 2026-08-26 — A gold passage is a verse range within one chapter, never a whole chapter or book. Reason: a chapter-wide gold entry cannot distinguish good retrieval from lucky retrieval.
- 2026-08-26 — Known limitation, measured in P2: TSK and Nave's index the 66 protestant books only, so Deuterocanon passages are reachable by vector and keyword search alone. Questions g19 and g20 exist to measure this. No fix is built until P2 numbers show one is needed.
- 2026-08-26 — Pericopes remain WEB paragraphs; no headings are added. P2 reports paragraph length distribution and recall before any change is considered. Reason: no public-domain heading set exists, and generated headings would inject interpretation.
- 2026-08-26 — A MUST candidate must carry at least two of the three origins (Nave's, FTS, TSK); a single-origin passage drops to SHOULD rather than being discarded. Reason: a passage the answer cannot omit should be corroborated by more than one source, and a passage that is right but uncorroborated is still recoverable from SHOULD.
- 2026-08-26 — Nave's topic weight falls as the topic grows (3.0 * 200/(200+n) per verse). Reason: membership of a 40-verse topic is strong evidence about a verse and membership of an 1855-verse topic is nearly none; unweighted, the large topics filled MUST lists with passages that shared a theme but did not answer the question.
- 2026-08-26 — Candidate ranges are ranked by score density, total score divided by the square root of the range length. Reason: without it a long range wins on volume alone.
- 2026-08-26 — Keywords use WEB vocabulary, notably "fear of Yahweh" rather than "fear of the Lord". Reason: the WEB Classic renders the divine name as Yahweh, so the conventional phrasing matches nothing.

## P2 session, 2026-08-26

- 2026-08-26 — Gold lists are approved as drafted. They are index-derived (Nave's, TSK, FTS) and unreviewed by a pastor; docs/EVAL.md and data/eval/questions.json say so in those words. Jared is not a pastor and declines to hand-judge; a future contributor may revise. Reason: honest standard for a scripture-only tool; no better ground truth exists at zero cost.
- 2026-08-26 — The six Deuterocanon passages set aside in the P2-prep handoff are added to the g19 and g20 MUST lists, tagged deutero, approved the same way. Reason: without them the canon test measures nothing.
- 2026-08-26 — Because the gold lists share sources with the topic, cross-reference and keyword retrieval paths, full-pipeline recall against them is near-circular; it is reported but not treated as evidence. The primary retrieval metric is ablation: vector-only recall@25 against MUST. Reason: measures what embeddings add, which is the only open question.
- 2026-08-26 — Vector store is plain float32 BLOBs in SQLite tables, searched brute force by cosine. sqlite-vec is not used. Reason: about 70,000 small vectors search in milliseconds, and no native extension has to be bundled into the installer. PLAN 3.2 updated and the sqlite-vec VERIFY item in section 16 struck.
- 2026-08-26 — The embedding and reranker models must run under llama.cpp at runtime, and index-time embeddings are produced through llama.cpp too, so index and query vectors come from identical code. Reason: eliminates train/serve mismatch.
- 2026-08-26 — PLAN 7.2 amended: the passage panel shows the full retrieved and expanded set grouped by book, cited passages marked and the rest collapsed one click away, with matched Nave's topics shown by name and their full verse lists. Reason: the reader chooses what to read; scripture-first.
- 2026-08-26 — PLAN 5.6 and 7.2 amended: two answer modes, the default themed synopsis over the top ~25 passages and, on demand, a themed summary of the entire retrieved set built in batches and merged, with the citation verifier applied at every stage including the merge. Never the default; P3 measures latency and quality first. Reason: full-set reading is impractical, and the summary must still be verifiable.
- 2026-08-26 — The MUST size rule is amended for g19 and g20 only, which now carry 14 entries: the 8 drafted protestant passages plus 6 deuterocanonical ones. Reason: deuterocanonical passages can never clear the two-origin bar because neither study corpus indexes those books, so without adding them by hand the canon toggle has nothing to be measured against.
- 2026-08-26 — Deuterocanonical MUST entries are exempt from the two-origin corroboration rule and carry origins ["fts"] alone. Reason: keyword search is the only origin available to them; the exemption is asserted in the tests so it cannot silently widen.
- 2026-08-26 — Gold ranges exclude verses the WEB omits. Sirach 19:20-22 stores verses 20 and 22 only, because 19:21 has no text. Reason: a gold list must not claim a verse the index cannot produce.
- 2026-08-26 — Documents longer than the embedding model context are truncated to fit rather than skipped, and the truncation is applied to the text after the model prefix. Reason: llama-server refuses an over-long input outright, and a refused document would leave a silent hole in the index; a truncated vector is worse than a full one but far better than none.
- 2026-08-26 — Some Nave's subtopic headings are long prose rather than headings, the longest running to 1,243 tokens. They are embedded truncated. Reason: P1 derived subtopic labels from the entry text, and Nave's writes some subtopics as full sentences; re-deriving them is a P1 change and is not worth reopening for a handful of rows.
- 2026-08-26 — llama-server is started with a physical batch of at least 2048 regardless of the model context. Reason: the batch must hold the longest single input, which is a different constraint from the context window, and a smaller batch makes the server reject long documents outright.
- 2026-08-26 — RECOMMENDED, confirmed in P3: embedding model nomic-embed-text-v1.5 (Apache-2.0, 137M, dim 768). Reason: it leads on every configuration measured and its 2048-token context leaves only 3 pericopes needing a split against bge-small's 106, while costing 251 MB resident against qwen3's 946 MB; the gap over both is inside the confidence interval, so the tie is broken on size and context, not on a claimed win.
- 2026-08-26 — RECOMMENDED, confirmed in P3: no reranker. Reason: bge-reranker-v2-m3 lowered recall@25 for all three embedding models, from 0.629 to 0.529 for the recommended one, while adding about 10 seconds per query and 2 GB of resident memory against 3 to 24 milliseconds for retrieval itself. It is the only reranker that met the licence and GGUF conditions, so "no reranker" is the finding rather than a preference.
- 2026-08-26 — RECOMMENDED, confirmed in P3: configuration F, vector verses plus vector pericopes plus FTS, fused by reciprocal rank fusion, then Nave's topic expansion and one TSK hop. Reason: highest recall of the configurations that ship, and the expansions are what fill the passage panel that PLAN 7.2 now specifies.
- 2026-08-26 — qwen3-embedding-0.6b is rejected as the default. Reason: its advantage over nomic is +0.034 recall@25 with a 95 per cent bootstrap interval of [-0.045, +0.112], which includes zero, against 3.8 times the resident memory, a 2.7-hour index build rather than 23 minutes, and 275 MB rather than 206 MB added to the installer.
- 2026-08-26 — bge-small-en-v1.5 is retained as the fallback embedding model if P3's hardware floor proves tight. Reason: 75 MB resident and 102 MB of vectors, at a recall cost that this eval set cannot prove is real.
- 2026-08-26 — Canon mode is confirmed not to be a filter over a fixed ranking: enabling the Deuterocanon displaces 5 to 15 of the 25 protestant passages, for every model and configuration tested. Reason: measured in P2; no code may assume the 66-book result is a subset of the both-canon result, and P5 must decide whether a reader turning the setting on should be told they will see different protestant passages.

## P3 session, 2026-08-26

- 2026-08-26 — The graded set for P3 is 10 questions: g01, g03, g04, g05, g08, g11, g12, g13, g14, g18. The other ten graded questions keep their gold lists but move to the smoke pool, which becomes 30 questions, of which P3 runs 10 and 20 are reserved for post-v1 testing. Reason: Jared's direction; exhaustive testing happens after v1.0.0, not now.
- 2026-08-26 — Canon priority: every gate, selection, smoke run, summarize-all test and hardware-floor number is measured in canon 66 only. Deuterocanon results are reported separately and never gate. Reason: the 66 books are the product.
- 2026-08-26 — Execution is strictly sequential: one chat model loaded at a time, one question at a time, llama-server run with a single slot and no parallel requests, and each question's metrics row written before the next begins. Reason: one thing at a time, and a partial session still leaves usable committed evidence.
- 2026-08-26 — Machine safety: llama.cpp uses its default thread count, no model is loaded whose GGUF size plus 2 GB headroom exceeds free RAM, never two model processes at once, and both server and harness run below normal priority. Reason: the machine must stay usable and must never swap.
- 2026-08-26 — Additive canon retrieval: in both-canon mode the harness runs retrieval under canon 66 exactly as in 66 mode, then a Deuterocanon-only retrieval, and appends its top slice (default 8) labeled. The 66 result is therefore always a subset of the both result. Reason: P2 measured up to 15 of 25 protestant passages displaced when the Deuterocanon was simply unfiltered.
- 2026-08-26 — The embedding model (nomic-embed-text-v1.5, sha256 in EVAL.md) is bundled in the installer rather than downloaded on first run. Reason: it is essential to every query, it is 262 MB, and it is one fewer download that can fail. P6 confirms.
- 2026-08-26 — No reranker in v1. Reason: P2 measured a recall@25 loss from 0.629 to 0.529 with 2 GB and about 10 seconds of cost.
- 2026-08-26 — No answer-quality rating rubric and no Jared rating pass. Smoke answers are written to docs/SMOKE.md for optional reading. Reason: the measured gates are fabricated-reference count and citation precision; a 1-to-5 rubric on 10 questions would add a number without adding evidence.
- 2026-08-26 — Prompts live in data/prompts/ as plain text with a version line: rewrite, synopsis, retry, summarize_batch, summarize_merge, all version 1. Reason: a prompt is part of the product's behaviour, so it is versioned and diffable rather than buried in code; every change gets its own DECISIONS line.
- 2026-08-26 — P3 gate thresholds, fixed before the 4B and 8B results were seen. (1) First-pass verifier violation rate at or below 0.30. Reason: a violation costs a full second generation, so a third of questions taking roughly twice as long is the most latency the retry path may add. (2) Fallback rate below 0.10, per the session brief. (3) Structure compliance 100 per cent, scored as the brief defines it: theme headings present, every theme cites at least one sent token, no theme cites an unsent token. (4) Median end-to-end latency at or below 180 seconds on this CPU, with no question above 300. Reason: three minutes is already a long wait for a desktop answer, and the plan's hardware floor has to be honest about it.
- 2026-08-26 — Structure compliance is scored from the stored outputs by pipeline/report_p3.py, using one definition for every model, because the harness's own check was tightened mid-session after the first model had already run. Reason: a metric must mean the same thing for every candidate it compares.
- 2026-08-26 — The retry loop is citation-only by design (docs/VERIFIER.md). A structurally poor but citation-clean answer is not retried. Reason: the verifier's contract is references, and widening it to prose shape would make the Rust port in P4 a style judge as well as a citation checker.
- 2026-08-26 — SELECTED: default chat model Qwen3-8B (Q4_K_M, Apache-2.0); fallback Qwen3-1.7B (Q8_0, Apache-2.0). Qwen3-4B fails two gates and is rejected. Reason: applying plan 6.4 to the gate results, the smallest model passing every gate is 1.7B and so becomes the fallback, and the next size that passes is 8B, because 4B fails structure compliance at 0.70 and exceeds the 300-second ceiling at 377.9 seconds on one question.
- 2026-08-26 — Qwen3-4B is rejected despite sitting between the two chosen sizes. Reason: 30 per cent first-pass violations, structure compliance 0.70 with three answers carrying no theme heading at all, citation coverage 0.333 against 0.79 and 0.82 for its neighbours, and a 377.9-second worst case. Size did not order quality here.
- 2026-08-26 — All three chat candidates come from the Qwen3 family. Reason: it is the only current-generation family offering Apache-2.0 weights with first-party GGUF builds at all three size classes, and holding the family constant makes size the variable that plan 6.4 actually selects on. Phi-4-mini (MIT) is the alternative family if P4 or later wants a cross-check.
- 2026-08-26 — Qwen3 reasoning is disabled with its own /no_think switch and any <think> block is stripped before verification. Reason: the reader never sees reasoning tokens, so they must not be part of what the verifier checks, and leaving them on multiplies latency for output nobody reads.
- 2026-08-26 — FINDING, not yet acted on: model query rewriting lowers retrieval recall for every candidate, by 0.162, 0.262 and 0.250 recall@25 against the hand-written keyword lists. This contradicts the expectation behind PLAN 5.2. Reason to flag rather than change: 5.2 is an approved plan decision and 10 questions is a small sample; P4 should measure it again before the rewrite step is kept, dropped, or made additive to the raw question.
